# تقرير للمبرمج: بروتفوليو الشركة الديناميكي  
## ومنه إلى منتج أعمال لمؤسسات وشركات

**المشروع المرجعي:** موقع شركة البستنجي للحلول البرمجية والتدريب (BAIT PAIT)  
**الجمهور:** المبرمج / فريق المنتج  
**الغرض:** شرح مفهوم البروتفوليو، كيف صار ديناميكياً في هذا المشروع، وكيف يُحوَّل إلى عمل تجاري يبيع «بروتفوليوهات» جاهزة وقابلة للإدارة للمؤسسات، **مع وكيل ذكاء اصطناعي من شركة البستنجي يعمل بـ RAG على قاعدة بيانات المشترك نفسه**.

---

## 1) ما هو بروتفوليو الشركة؟

بروتفوليو الشركة (Company Portfolio) ليس «معرض صور». هو **الواجهة الرسمية لإثبات القدرة**: ماذا بنينا، لمن، في أي قطاع، وبأي جودة بصرية يمكن التحقق منها.

للمبرمج، البروتفوليو طبقة بيانات + طبقة عرض:

| الطبقة | السؤال الذي تجيب عنه |
| --- | --- |
| الهوية | من نحن؟ الاسم، الشعار، الرؤية، الرسالة، أرقام الإنجاز |
| الأعمال | ماذا أنجزنا؟ كل عمل = سجل له اسم، قطاع، عائلة منتج، غلاف، رابط |
| الثقة | لماذا نصدّق؟ شعارات حقيقية، NDA واضح، قنوات تواصل حية |
| الحركة | كيف يتغيّر؟ إضافة عمل جديد بدون إعادة برمجة الصفحة |

في BAIT PAIT البروتفوليو هو قسم **أعمالنا**: 23 تطبيقاً بشعارات Play Store، مجمّعة بعائلات (سوبر سبيد، جايك، أفندي…) ومفلترة بقطاعات (طعام، إنتاجية، نمط حياة، أعمال). هذا أقوى من قائمة روابط؛ يعطي الزائر **خريطة منتجات** لا لائحة عشوائية.

## 2) الفرق بين بروتفوليو ثابت وديناميكي

### ثابت (Static)

الأعمال مكتوبة داخل الكود (`src/lib/works.ts`). أي تطبيق جديد = تعديل ملف، ثم بناء ونشر. مناسب للإطلاق الأول، غير مناسب لشركة تضيف منتجات أسبوعياً أو لعميل غير تقني.

### ديناميكي (Dynamic) — ما نُفّذ هنا

المصدر الحي أصبح ملفاً يُدار من لوحة التحكم:

1. المشرف يدخل `/admin/works`
2. يضيف اسماً، قطاعاً، عائلة، ويرفع شعاراً
3. `POST /api/admin/works` يحفظ في `data/works.json`
4. الصفحة الرئيسية `force-dynamic` تقرأ `getWorks()` وتعرض العمل فوراً

**القاعدة للمبرمج:** العرض لا يعرف القائمة مسبقاً. يعرف فقط شكل السجل (`Work`) ويعرض المصفوفة القادمة من المخزن.

نفس الفكرة طُبّقت على الهوية (`data/settings.json`) والرسائل (`data/messages.json`). البروتفوليو الديناميكي جزء من **موقع يُدار كمنتج** وليس صفحة HTML مجمّدة.

## 3) كيف يعمل الديناميك في هذا المشروع (تدفق حقيقي)

```
الزائر  →  src/app/page.tsx  →  getWorks() / getSettings()
                                      ↓
                              data/works.json
                              data/settings.json
                                      ↑
المشرف  →  /admin/works + /admin/settings
        →  /api/admin/works  /api/admin/settings  /api/admin/upload
        →  public/works/{slug}-{stamp}.{ext}

العميل  →  نموذج التواصل  →  POST /api/contact  →  data/messages.json
                                                 →  /admin/messages
```

### نموذج العمل `Work`

```ts
type Work = {
  id: string;            // slug ثابت لا يتغير عند التعديل
  name: string;          // الاسم العربي للعرض
  nameEn: string;        // الاسم اللاتيني / المتجر
  sector: WorkSector;    // food | productivity | lifestyle | business
  category: string;      // تسمية القطاع للواجهة
  family: string;        // عائلة المنتج (تجميع سوبر سبيد / جايك…)
  note?: string;
  cover: string | null;  // مسار الغلاف بعد الرفع
  notification: string | null; // جاهز لصور إشعار لاحقاً
};
```

### دروس تقنية مستخرجة من التنفيذ

- **البذرة مرة واحدة:** أول قراءة لـ `works.json` تنسخ `WORKS` من الكود. إذا حذف المشرف الكل، القائمة تبقى فارغة (لا إعادة بذر صامتة).
- **الفصل بين الكود والبيانات:** الكود يعرف العقد (schema). البيانات ملك التشغيل و`data/*.json` خارج Git.
- **رفع مقيّد:** jpeg/png/webp حتى 6MB إلى `public/works/`.
- **الظهور الفوري:** لا كاش صفحة ثابتة على الرئيسية.
- **NDA كحقل إعدادات:** البروتفوليو الاحترافي يقول أيضاً ماذا *لا* يُعرض.

هذا هو الحد الأدنى لمنتج «بروتفوليو يُدار» بدون قاعدة بيانات ثقيلة. مناسب لـ MVP وعميل واحد على سيرفر واحد.

## 4) حدود النسخة الحالية (مهم قبل بيعها كمنتج)

ما بُني كافٍ **لشركة واحدة**. لا يكفي بعد كمنصة SaaS:

| الحد | الأثر |
| --- | --- |
| مستأجر واحد (tenant واحد) | لا يوجد `companyId`؛ كل البيانات في مجلد `data/` واحد |
| تخزين ملفات JSON | لا تزامن بين سيرفرات، لا نسخ احتياطي مدمج، تعارض كتابة محتمل |
| مشرف واحد بكلمة مرور | لا أدوار (محرر / مشاهد / عميل) |
| لا دومين لكل عميل | الموقع هو BAIT PAIT فقط |
| لا صفحات عمل تفصيلية | البطاقة غلاف + اسم + قطاع، بلا دراسة حالة |
| لا صلاحيات NDA متدرجة | نص واحد للجميع |

أي حديث عن «مشروع بزنس على شكل بروتفوليوهات» يجب أن يعتبر النسخة الحالية **قالباً مرجعياً (reference implementation)** لا المنتج النهائي.

## 5) فكرة العمل: منصة بروتفوليوهات للمؤسسات

### المشكلة

كل شركة/مؤسسة تحتاج واجهة ثقة: أعمال، هوية، تواصل. اليوم تدفع لمبرمج في كل تحديث، أو تبقى موقعها قديماً. المؤسسات التعليمية، شركات البرمجيات، مكاتب الهندسة، عيادات المجموعات، والجمعيات كلها نفس الحاجة بهوية مختلفة.

### الحل

منتج اسمه المقترح: **Portfolio OS** (نظام تشغيل البروتفوليو):

- قالب موقع احترافي (عربي RTL جاهز، كما في BAIT PAIT)
- لوحة تحكم يديرها موظف غير تقني
- كل مؤسسة = مستأجر: أعمالها، ألوانها، نطاقها، رسائلها
- الشركة البائعة (البستنجي) تبيع الاشتراك + التخصيص + التدريب
- **وكيل ذكاء اصطناعي تابع لكم** يجيب من محتوى البروتفوليو **ومن قاعدة بيانات المشترك** عبر RAG وصلاحيات صريحة

هذا يحول «صنعنا موقعنا» إلى **صنعنا المصنع الذي يصنع مواقع البروتفوليو + مساعد قرارات مربوط ببيانات العميل**.

### من يشتري؟

1. شركات برمجيات تريد معرض تطبيقات يُحدَّث أسبوعياً  
2. مؤسسات تدريب تريد عرض البرامج والخريجين  
3. مكاتب خدمات (محاماة، هندسة، تسويق) تريد دراسات حالة بلا مطور  
4. هيئات ومؤسسات تريد «منجزات العام» مع أرشف شفاف  
5. وكالات تعيد بيع القالب لعملائها (white-label)

## 6) المعمارية المقترحة للمنتج (للمبرمج)

ارتقِ من ملف JSON إلى عقد واضح متعدد المستأجرين، مع الإبقاء على نفس تجربة اللوحة.

```
Tenant
  id, slug, domain, plan, locale, theme
  settings     → هوية، رؤية، تواصل، أرقام
  works[]      → البروتفوليو
  taxonomies[] → قطاعات/عائلات قابلة للتعريف لكل مستأجر
  leads[]      → الرسائل
  media[]      → ملفات الغلاف (object storage)
  users[]      → أدوار
  agent        → وكيل BAIT PAIT: سياسات، أدوات، فهرس RAG
  connectors[] → ربط قاعدة المشترك (Postgres/MySQL/SQL Server…) بتفويضه
```

**مسارات عامة:** `https://{slug}.portfolio.baitpait.com` أو دومين العميل  
**مسارات إدارة:** `https://app.portfolio.baitpait.com/{tenant}/admin`

طبقات مقترحة:

| الطبقة | الخيار العملي للمرحلة 1 | المرحلة 2 |
| --- | --- | --- |
| تطبيق الواجهة | Next.js قالب واحد + ثيم لكل مستأجر | متغيرات قوالب (عيادة / وكالة / SaaS) |
| البيانات | Postgres + صفوف `tenant_id` | نفسه + بحث full-text |
| الملفات | S3 / Cloudflare R2 | CDN + تحويل أحجام |
| المصادقة | مستخدمون لكل مستأجر | SSO للمؤسسات |
| النشر | حاوية واحدة + جدول نطاقات | edge لكل موقع |
| الوكيل | RAG على أعمال/إعدادات المستأجر فقط | RAG + أدوات قراءة على DB المشترك |

لا تبدأ بميكروسيرفس. ابدأ بـ **نفس لوحة BAIT PAIT** مع عمود `tenantId` وكل طلب يُفلتر به.

## 7) ماذا يبقى من هذا المشروع كما هو؟

قابل لإعادة الاستخدام مباشرة:

- عقد `Work` + العائلات والقطاعات  
- شاشات الأعمال/الإعدادات/الرسائل  
- رفع الشعار ومسار الظهور الفوري  
- فكرة NDA والفلاتر  
- القالب البصري RTL/زجاجي كأحد الـ themes

يُستبدل لاحقاً:

- `data/*.json` → جداول  
- كوكي مشرف واحد → حسابات  
- `force-dynamic` لكل الصفحة → كاش حسب المستأجر مع إبطال عند الحفظ

## 8) نموذج إيرادات مبسّط

ثلاث طبقات كافية للإطلاق:

1. **إطلاق (Setup):** تصميم الهوية ورفع الأعمال الأولى — دفعة واحدة  
2. **اشتراك شهري/سنوي:** الاستضافة، اللوحة، النسخ الاحتياطي، الدومين  
3. **إضافات:** صفحة دراسة حالة، لغات، تكامل واتساب/CRM، تدريب فريق العميل  
4. **وكيل BAIT PAIT (طبقة أعلى سعراً):** مساعد داخل لوحة المشترك يقرأ البروتفوليو **وقاعدة بياناته** بالإذن — تقارير، بحث، مسودات محتوى، إجابات تشغيلية بلا تسريب بين العملاء

قيمة البيع ليست «موقع». القيمة المزدوجة:

1. **الموظف يضيف مشروعاً في دقيقتين فيظهر للجمهور**  
2. **الموظف يسأل وكيلكم بالعربية فيجيب من بياناته هو، لا من إنترنت عام**

## 9) MVP تجاري (90 يوماً منطقياً)

**الشهر 1 — القالب المنتج**  
استخراج موقع BAIT PAIT إلى قالب: متغيرات الألوان، الشعار، النصوص، الأعمال من API.

**الشهر 2 — تعدد المستأجرين الخفيف**  
جدول شركات + عزل البيانات + نطاق فرعي لكل عميل + لوحة الدخول.

**الشهر 3 — أول 3 عملاء مدفوعين**  
شركة برمجيات، مكتب خدمات، جهة تدريب. قياس: وقت إضافة عمل جديد، وكم مرة استُخدمت اللوحة بلا مطور.

لا تُبنَى سوق قوالب عامة قبل إثبات أن **غير المبرمج** يدير البروتفوليو أسبوعياً.

**بعد أول 3 عملاء — الشهر 4 للوكيل:**  
اتصال تجريبي بقاعدة واحدة للعميل (قراءة فقط + جداول مصرّح بها + فهرس RAG). لا يُفتح الوكيل على كل الجداول دفعة واحدة.

## 10) وكيل الذكاء الاصطناعي من البستنجي + RAG على قاعدة المشترك

هذه الطبقة هي **التمييز التنافسي**: البروتفوليو الواجهة؛ الوكيل العقل الذي يعمل داخل بيانات المؤسسة بعد موافقتها.

### ماذا يفعل الوكيل؟

يُنشأ **وكيل باسم BAIT PAIT** داخل لوحة كل مشترك. لا يتدرّب على خلط بيانات كل العملاء في نموذج واحد عام. لكل مستأجر:

1. **معرفة البروتفوليو:** الأعمال، العائلات، الهوية، الرسائل، الـ NDA — كما في `Work` و`SiteSettings`.  
2. **معرفة قاعدة المشترك:** بعد أن يربط العميل قاعدته (قراءة مصرّح بها) يفهرس الوكيل المخطط والوثائق والصفوف المسموحة، ويجيب بـ RAG + أدوات استعلام محدودة.  
3. **معرفة الملفات:** عقود، كتالوجات، أدلة تشغيل يرفعها العميل إلى مساحة المستأجر فقط.

أمثلة أسئلة يحلها للمشترك لا للزائر العام:

- «كم منتجاً في عائلة جايك وما قطاعاتها؟» → من بروتفوليو المنصة  
- «ما أعلى 10 أصناف مبيعاً هذا الشهر حسب جدول الطلبات عندنا؟» → من قاعدة المشترك بعد الإذن  
- «صغ لي فقرة معرض من المشاريع العامة فقط مع احترام الـ NDA» → يدمج الاثنين بلا كشف سجلات خاصة على الموقع العام

الموقع العام **لا** يفتح قاعدة العميل للزوار. الوكيل قناة داخلية للمشترك (وموظفيه بصلاحيات).

### مسار تقني للمبرمج (عقد صارم)

```
موظف المشترك (جلسة tenant)
    → وكيل BAIT PAIT (سياسة المستأجر فقط)
        → استرجاع RAG: فهرس vector خاص بـ tenant_id
        → أدوات مصرّحة: schema.describe / query.readonly / portfolio.search
        → قاعدة المشترك عبر Connector (اعتماد العميل، شبكة معزولة)
    → إجابة + مصادر (أي جدول/مستند استُخدم)
    → سجل تدقيق: من سأل، ماذا استُرجع، هل مُنع
```

قواعد لا تُكسر:

| القاعدة | المعنى الهندسي |
| --- | --- |
| عزل المستأجر | كل فهرس RAG وكل اتصال DB مقيّد بـ `tenant_id`. لا استعلام عبر العملاء |
| تفويض صريح | العميل يضيف Connector: مضيف، قاعدة، مستخدم DB بصلاحية قراءة، قائمة جداول/أعمدة |
| قراءة أولاً | المرحلة 1: `SELECT` على جداول allowlist فقط. لا INSERT/UPDATE/DELETE عبر الوكيل حتى سياسة كتابة منفصلة |
| لا أسرار في الـ prompt | سلسلة الاتصال في خزنة (secrets manager) لا تُمرَّر للنموذج |
| RAG على المخطط ثم الصفوف | فهرسة `information_schema` + عيّنات/تجميعات مصرّحة، لا صب القاعدة كاملة في السياق |
| حجب الأعمدة | هواتف، كلمات مرور، بطاقات، حقول `pii` تُستثنى من الفهرس والأدوات |
| الموقع العام منفصل | الزائر يرى `works` العامة فقط. الوكيل لا يُستدعى من الواجهة العامة إلا بوضع FAQ مُصفّى يدوياً |
| تدقيق | كل أداة تُسجَّل. يمكن للعميل قطع الـ Connector فوراً |

### مكوّنات التنفيذ المقترحة

- **Orchestrator:** وكيل بأدوات (tool calling) لا نموذج «يتكلم SQL بحريّة».  
- **Query tool:** يولّد SQL من السؤال ثم يمر على مدقّق: جدول مسموح؟ لا `JOIN` لجداول محجوبة؟ حد صفوف (مثلاً 200)؟ مهلة؟  
- **RAG store:** متجهات لكل مستأجر (أعمال المنصة + وصف الجداول + مستندات مرفوعة).  
- **Connector:** نفق أو IP allowlist من شبكتكم إلى DB العميل، أو نسخة قراءة (read replica) يوفّرها هو.  
- **سياسة الإجابة:** إن لم يجد مصدراً في فهرس المستأجر يقول «لا أعلم من بياناتكم» بدل اختراع أرقام.

### لماذا هذا يبيع؟

المؤسسة لا تشتري شاتاً عاماً. تشتري **مساعداً يعرف كتالوجها المعروض للناس، ويعرف تشغيلها الداخلي**، مع بقاء البيانات عندها. البستنجي تبيع الثقة + القالب + الوكيل كحزمة واحدة: الواجهة للجمهور، والوكيل للإدارة.

## 11) مخاطر يجب أن يخطط لها المبرمج

- **محتوى العميل:** شعارات وعلامات تجارية؛ يلزم تفويض رفع الأصول  
- **NDA:** بعض الأعمال لا تُعرض؛ يلزم حالة `visibility: public | private | nda`  
- **الأداء:** مئات الصور بدون تحويل أحجام تُفشل الجوال  
- **عزل البيانات:** خطأ `tenantId` يعرض أعمال شركة لأخرى — هذا كسر ثقة لا يُصلح بـ hotfix تجميلي  
- **التسعير المحلي:** المؤسسات تفضّل دفعة + صيانة سنوية أحياناً أكثر من SaaS شهري؛ ابنِ الفوترة مرنة  
- **الوكيل على قاعدة العميل:** تسريب `tenant_id` أو سلسلة اتصال = حادث خصوصية. ابدأ بقراءة فقط، allowlist، خزنة أسرار، وقطع فوري للـ Connector  
- **هلوسة الأرقام:** أي رقم تشغيلي يجب أن يُرفق بمصدر جدول/تجميع أو يُرفض  
- **امتثال:** اتفاقيات معالجة بيانات (DPA) مع المشترك قبل ربط أي قاعدة إنتاج

## 12) توصية ختامية

عرّف البروتفوليو للمبرمج كالتالي:

> **البروتفوليو الديناميكي = نموذج بيانات أعمال + واجهة إدارة + قناة نشر فورية.**  
> **الوكيل = طبقة أسئلة فوق هذا النموذج + فوق قاعدة المشترك بعد إذن صريح، معزولة لكل مستأجر.**  
> الموقع الواجهة مجرد reader للعام. الوكيل reader داخلي بسياسات.

مشروع البزنس ليس «نسخ موقع البستنجي لكل زبون يدوياً». المشروع هو:

**نظام يُنشئ لكل مؤسسة بروتفوليو حي بهويتها، تديره هي، وفوقه وكيل ذكاء اصطناعي من البستنجي يجيب من أعمالها المعروضة ومن قاعدة بياناتها الخاصة عبر RAG — يُباع كاشتراك مع قالب أثبت نفسه في BAIT PAIT.**

الخطوة الهندسية التالية الأنسب:

1. استخراج `Work` / `SiteSettings` / لوحة الأعمال إلى `packages/portfolio-core` وتشغيل مستأجر ثانٍ.  
2. إضافة وكيل داخلي يقرأ بروتفوليو المستأجر فقط (بدون DB خارجي).  
3. بعدها Connector قراءة + RAG على جداول يختارها المشترك. لا تعكس الترتيب: لا تربط قواعد زبائن قبل عزل المستأجرين.
